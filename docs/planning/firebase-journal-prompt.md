## 身分與時間
每筆對應 Firebase Auth 的 UID，登入方式取自 Auth；預設私人資料只供本人存取。
區分：本次登入認證時間、開始／最後編輯時間（客戶端）、點擊保存時間（客戶端）、資料庫成功保存時間（伺服器）。
保存時間以 serverTimestamp 為準；登入 auth_time 的來源與驗證方式須說清楚，不能把頁面自行填寫的時間當作可信稽核。
時間以 UTC 儲存，畫面用 Asia/Taipei 顯示，並保存使用者時區。客戶端時鐘偏差不得影響主排序。
只存必要身分資訊；不保存密碼、ID token、refresh token、私鑰或完整登入憑證。

## 最小架構、權限與可靠性
若確認適合 Firestore，優先評估 Firebase Auth + 官方 Web SDK + 私人使用者資料路徑，例如 users/{uid}/tradeRecords/{recordId}；這只是候選結構，確認產品／版別後才定案。
私人 MVP 優先不新增自建後端或 Cloud Functions；若有不可被客戶端偽造的稽核或統計需求，再說明可信伺服器為何必要。使用者自填日誌不等於交易所驗證資料。
提出 Security Rules：依 request.auth.uid 與路徑確認所有權；個人版額外限制核准 UID；驗證型別、有限數值、合理範圍、欄位白名單與 server timestamp。
拒絕跨帳戶讀寫、未登入存取、變更 owner／建立時間／歷史快照；實際成交結果以獨立欄位或子記錄更新，並保留修訂紀錄。
規則必須在 Emulator 驗證，不能使用公開讀寫或「只要登入即可讀全部」。
Firebase Web config 並非管理員憑證；服務帳戶與私鑰不得進公開 repo。評估 API 限制、App Check 與必要的成本控制，不能拿 App Check 代替 Auth／Rules。
「輸出記錄」保存前驗證有效試算、已選週期及標的；選擇其他時需正整數分鐘。
不合格試算先提出「禁止保存」或「保存為不可交易草稿」的取捨，再由我決定；不能當成可開單或已成交。
設計未登入、保存中、成功、失敗、離線狀態；成功僅在伺服器確認後顯示。失敗保留表單，重試沿用同一 recordId／冪等 ID，快速連點、逾時重試或重新整理不能產生重複紀錄。
若啟用離線持久化，評估共用電腦與登出後殘留資料；不得默默啟用。
歷史列表預設時間倒序、分頁／限量讀取，支援方向、標的、週期、狀態與日期篩選；提出必要索引，不全量監聽歷史。
提供私人 JSON／CSV 匯出、備份與復原方案，CSV 防公式注入；匯出另用「下載 CSV」，不要混淆「輸出記錄」保存動作。刪除策略與保留期限待我決定。

## 實際交易與績效
試算保存後預設狀態為 planned（未確認成交），不列入實際績效。
提出 planned、open、closed、cancelled 的簡單狀態流；closed 必須有完整實際結果，cancelled 不列入勝率。
第一版績效可先採單筆完整開／平倉；分批入場、分批平倉、追加保證金先列為後續擴充，不能使用單一平倉價假裝完整支援。
實際結果需記錄：成交時間、實際入場／平倉均價、實際幣數／張數與合約面值、實際槓桿／保證金、平倉原因、實際手續費、資金費、實際淨損益，以及資料來源為手填或匯入。
資金費收入為正、支出為負；開倉／平倉手續費不能重複扣除。若填交易所已扣費淨損益，明確標記哪些費用已包含；不得再套用試算費率。
原始試算快照保持不變，讓我比較計畫與實際差異。
績效僅統計已平倉且完整的記錄，先提供：筆數、淨損益、勝率、平均盈利／虧損、Profit Factor、平均實際 R；列出清楚定義與零筆／無虧損／打平處理。
實際 R 的分母採保存時的初始 plannedLoss（含原假設成本），分母<=0時不計；這是比較基準，不重算原風險模型。
百分比報酬須說明分母是總資金還是保證金，不能混用槓桿 ROI 與帳戶報酬。
沒有入出金及未平倉損益，就不能宣稱完整帳戶收益率、帳戶最大回撤或年化績效；可以另標「已平倉累計損益曲線／回撤」。
